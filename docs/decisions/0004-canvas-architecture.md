# ADR-0004: Canvas architecture — scene registry, View tracking, shader pipeline

- **Status:** accepted
- **Date:** 2026-10-14
- **Task:** tasks/004-lab-canvas-architecture.yaml

## Context

Task 003 chose ViewTransition API for page transitions. The canvas (`CanvasRoot`) survives every navigation since it lives in the root layout. Task 004 establishes the architecture that all future scenes will follow: how scenes register, how they position themselves against DOM elements, and how shaders import shared GLSL code.

Key constraints from `docs/WEBGL.md`:
- Exactly one `<Canvas>` in the tree.
- Scenes place themselves against DOM elements via drei `<View>`.
- Shaders use `#include "tokens.glsl"` for design constants.
- Static tier: canvas not mounted; scene container shows `poster.png`.

## Decision

### Scene placement: drei `<View>` + `<View.Port />`

`CanvasRoot` mounts `<View.Port />` inside the Canvas. Route components render `<ReferenceScene>` (or any scene wrapper) which renders a DOM container plus `<View track={ref}>`. Three portals the View content into the Canvas at the DOM element's position.

Considered alternatives:
- **Tunnel (react-tunnel)**: More explicit but adds a dependency and requires manual coordinate math. Three/drei already handle this correctly via IntersectionObserver in View.
- **Offscreen Canvas + Worker**: Maximum isolation but requires transferable proxy — no React integration, incompatible with R3F.

**Chosen**: drei View. Zero extra dependencies. The Lenis smooth-scroll creates a known risk (DOM rect may lag behind physical scroll), but in harness mode scroll is locked so snaps are deterministic.

### Scene registry: `src/gl/registry.ts`

Scenes register an id and a cleanup callback on mount; unregister on unmount. The registry is a plain Map — no React state, no global store. Currently only used for lifecycle logging; future uses: dispose textures/geometries on scene unmount.

### GLSL `#include` resolution: custom CJS loader

`src/gl/glsl-loader.cjs` is a webpack/turbopack loader that resolves `#include "file.glsl"` at bundle time (same search path as `scripts/shader-check.mjs`). No new npm dependency. Registered in `next.config.ts` for both Turbopack (dev) and webpack (prod builds).

`pnpm shaders` already resolves includes independently via its own Node.js resolver in `scripts/shader-check.mjs`.

### Shader token access: `#include "tokens.glsl"`

Shaders include `tokens.glsl` from `src/gl/glsl/generated/` (the generated file, not authored). Tokens regenerated with `pnpm tokens:build`. No literal design colors in GLSL.

### Static tier: `poster.png`

Scene wrapper checks tier. In static tier, renders an `<img>` pointing to `poster.png` in the scene folder. Poster is generated by `pnpm snap` at the harness URL for `t=0, progress=0`. Scene wrappers gracefully fall back to a neutral background if poster.png is absent (lab phase).

## Consequences

- Every new scene: one folder under `src/gl/scenes/<id>/` with `Scene.tsx`, `uniforms.ts`, `*.vert`, `*.frag`, `poster.png`.
- `#include "tokens.glsl"` works in any shader at any nesting depth.
- drei View aligns with DOM — may drift under Lenis smoothing. During harness snaps scroll is frozen so this doesn't affect visual tests.
- Registry cleanup hook is in place; actual resource disposal (geometries, textures) is left for individual scenes.

## Recommendation

Accept. The architecture adds zero new runtime dependencies, follows drei conventions, and produces deterministic harness snaps. The View/DOM alignment risk under Lenis is acknowledged and will be measured in task 005 perf budgets.
