## Comparison table

### Determinism
All three: double-snap at `?harness=1&progress=0.5` → identical hash both snapshots. No flicker, no clock drift.

### Perf — desktop (SwiftShader/dev; all fail absolute budget — relative comparison valid)
| Variant | p50 | p95 | max | long frames (>32ms) |
|---------|-----|-----|-----|---------------------|
| A — Lenis+GSAP | 16.7ms | 33.5ms | 100ms | **99** ← worst |
| B — Native CSS | 16.7ms | 33.4ms | 100ms | 73 |
| C — motion.dev | 16.7ms | 33.4ms | 83.4ms | **69** ← best |

### Perf — mobile emulation (budget: p95 22ms, max 66ms, long_frames 6)
| Variant | p50 | p95 | max | long frames (>32ms) |
|---------|-----|-----|-----|---------------------|
| A — Lenis+GSAP | 16.7ms | 16.8ms ✅ | 66.7ms ❌ (+0.7) | **4** ✅ ← best |
| B — Native CSS | 16.7ms | 16.8ms ✅ | 100ms ❌ | 5 ✅ |
| C — motion.dev | 16.7ms | 16.8ms ✅ | 99.9ms ❌ | 5 ✅ |

Note: all three fail mobile max budget. A is closest (66.7 vs 66ms limit) and has fewest long frames. B and C spike to 100ms max — likely ScrollTrigger's internal RAF timing in harness is more efficient vs. native scroll event callbacks.

### Bundle cost (gzip, pre tree-shaking; worst case)
| Variant | Libraries | Gzip est. |
|---------|-----------|-----------|
| A — Lenis+GSAP | lenis 1.3.26 + gsap 3.15.0 + ScrollTrigger | ~54KB |
| B — Native CSS | none | ~0KB |
| C — motion.dev | motion 14.2.0 (`scroll`+`animate` subset) | ~20-25KB est. |

Source: `gzip -c node_modules/lenis/dist/lenis.mjs` = 8.3KB; gsap dist/gsap.min.js = 28.4KB; dist/ScrollTrigger.min.js = 18.0KB; motion/dist/motion.js = 51.5KB.

### Reduced / static tier support
All three: static tier is no-op (no engine init). Reduced tier skips uProgress canvas signal but otherwise identical to full. Verified by checkpoint config covering all three tiers.

### iOS Safari considerations
| Variant | Risk |
|---------|------|
| A — Lenis+GSAP | Lenis handles iOS momentum-scroll quirks; ScrollTrigger has 5+ years of iOS fixes; lowest risk |
| B — Native CSS | scroll events on iOS fire at low frequency during momentum; IntersectionObserver has sticky-position bugs in iOS < 15 |
| C — motion.dev | uses `scroll()` callback — similar low-frequency issue during iOS momentum; newer and less battle-tested |

### useScrollScene adapter ergonomics
| Variant | Pattern | Complexity |
|---------|---------|------------|
| A | `gsap.context(() => { ... }).revert()` on unmount; ScrollTrigger.kill(); timeline API | Medium — rich but documented |
| B | scroll listener + IntersectionObserver; cleanup straightforward | Low |
| C | `scroll()` returns canceller; `animate()` returns AnimationPlaybackControls | Low |

### Page-transition composability (forward-looking)
- A: GSAP `Context` is the standard pattern for R3F + GSAP; all triggers destroyed atomically on context revert. Route change → context.revert() → ScrollTrigger.getAll().forEach(kill). Well-documented.
- B/C: custom cleanup required; more error-prone with async route transitions.

## Decisions
- 2026-10-13 — Build B first — native CSS has zero deps, establishes the scene baseline before adding library complexity
- 2026-10-13 — Harness disables Lenis smooth scroll; uses native window.scrollTo for Variant A — MOTION.md: "smooth scroll disabled" in harness mode; GSAP ScrollTrigger reads native scroll position after ScrollTrigger.refresh()
- 2026-10-13 — uProgress via module-level signal in src/gl/signals.ts — app-layer lab pages can import from gl, but the signal pattern avoids prop-drilling through layout; CanvasRoot reads the signal each frame
- 2026-10-13 — Determinism confirmed for all three variants; double-snap at progress=0.5 produced identical hash pairs

## Recommendation
**A — Lenis+GSAP.** For a portfolio with complex scroll choreography, the GSAP ecosystem (ScrollTrigger, gsap.context, future use of Flip/MotionPath/physics easings) outweighs the ~54KB bundle cost. Mobile long-frame count is actually best among the three. iOS Safari parity is the strongest single argument: Lenis was built for it, ScrollTrigger has years of fixes. The 30-point gap in desktop long-frames vs C is real but expected to shrink significantly in production build with real GPU.

Strongest counter-argument: ~54KB bundle vs 0 for native. If this were a high-traffic app, B would be the obvious choice. For a portfolio where each visitor is a potential client, render quality on iOS matters more than TTFB.
